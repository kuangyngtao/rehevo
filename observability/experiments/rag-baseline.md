# RAG 可重复基线

## 目的

对同一个已向量化知识库执行固定问题集，记录 API 端到端耗时、RAG 回答/检索计数和命中数。该基线衡量运行稳定性与性能，不把模型回答正确性宣称为完整质量评测；来源引用和 30—50 题效果集在 M2 实施。

## 固定条件

- 后端：`http://localhost:8080`
- 指标：`/actuator/prometheus`
- 知识库：本地验收样本（ID 仅用于 API 请求，不写入 Prometheus 标签）
- 请求数：3
- 运行日期：2026-08-15

## 问题集

1. 这份材料里的项目代号是什么？只回答代号。
2. 材料规定 Redis Stream 在什么条件后 ACK？
3. 材料中重复消费由什么机制处理？

## 记录格式

| 序号 | HTTP 状态 | 端到端耗时（秒） | 答案核对 | 备注 |
| --- | --- | --- | --- | --- |
| 1 | 200 | 25.698 | 通过：返回 `Orchid-417` | |
| 2 | 200 | 19.254 | 通过：回答“消费成功后才 ACK” | |
| 3 | 客户端超时 | 90.020 | 客户端未取得答案 | 请求断开后服务端仍完成，服务端 RAG 耗时约 317.029 秒 |

## 实际 Prometheus 差值

后端在本实验前刚重启，因此以下数值就是本次请求产生的增量：

| 指标 | 实测值 | 解读 |
| --- | --- | --- |
| 客户端可见成功率 | 2 / 3（66.7%） | 第 3 次在 90 秒客户端超时；两次完成请求均返回预期事实。 |
| 服务端 RAG 成功率 | 3 / 3（100%） | 第 3 次在客户端断开后仍完成，未被记录为服务端失败。 |
| `app_rag_answer_seconds_sum / count` | 361.644 / 3 = 120.548 秒 | 前两次为约 20—26 秒；第 3 次约 317.029 秒，拉高均值。 |
| `app_rag_retrieval_total{path="primary",status="success"}` | 3 | 三次请求均走主检索。 |
| `app_rag_retrieval_seconds_sum / count` | 1.343 / 3 = 0.448 秒 | 即使出现长尾，检索仍不是主要耗时来源。 |
| `app_rag_retrieval_hits_sum / count` | 3 / 3 = 1.0 | 每次检索命中 1 个 Chunk。 |
| `app_rag_query_rewrite_total{status="success"}` | 3 | 三次请求均完成 Query rewrite。 |

本样本只有三次服务端完成记录，不能据此宣称 P95。前两次 API 端到端最大值为 25.698 秒；第 3 次的“客户端 90 秒超时、服务端仍运行约 317 秒”是后续应补“HTTP 取消/超时联动与观测”的真实信号，不把它误写为模型或检索失败。
