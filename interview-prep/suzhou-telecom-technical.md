## 2. 项目一：AI 智能评测与知识问答平台

### 2.1 项目一句话

> 这是一个基于 Java 21、Spring AI、PostgreSQL/pgvector、Redis Stream、Apache Tika 和 WebSocket 的 AI 面试辅助平台，覆盖简历评估、模拟面试、语音面试、知识库问答、面试安排和多模型配置等 6 个业务模块。

### 2.2 技术栈

- 后端：Java 21、Spring Boot、Spring AI、Spring Data JPA、Redisson、Apache Tika、iText、WebSocket。
- 数据：PostgreSQL、pgvector、Redis、对象存储。
- AI：OpenAI 兼容模型、Qwen ASR/TTS、Prompt 模板、结构化输出、RAG。
- 前端：React、TypeScript、Vite、Tailwind CSS、SSE/WebSocket 交互。

### 2.3 可量化信息

可以说：

- 覆盖 `6 个业务模块`：简历管理、模拟面试、语音面试、面试安排、知识库问答、多模型配置。
- 内置 `11 个面试方向 Skill`，覆盖 Java 后端、系统设计、算法、前端、AI Agent 等方向。
- Redis Stream 承载 `3 类耗时任务`：简历分析、知识库向量化、报告生成。
- Apache Tika 具备多格式解析能力，项目重点适配 PDF、DOCX、Markdown、TXT 等常见格式。
- 评估链路支持分批评估、结构化输出、二次汇总和降级兜底。

不要说：

- “用户量多少多少”
- “准确率提升多少”
- “性能提升百分之多少”

除非你真的测过。

### 2.4 架构讲法

可以按四层讲：

1. 接入层  
   前端页面发起简历上传、面试创建、知识库问答、语音面试等请求；后端通过 Controller 暴露 REST 接口，语音模块使用 WebSocket，RAG 问答使用 SSE 流式返回。

2. 业务层  
   包括简历分析、模拟面试、知识库、语音面试、面试安排、多模型配置。每个模块有自己的 Service 和实体模型，核心 AI 调用能力尽量抽象复用。

3. AI 能力层  
   统一处理模型调用、Prompt 模板、结构化输出、向量化、相似度检索、RAG 拼接、流式响应。

4. 基础设施层  
   PostgreSQL 存业务数据，pgvector 存向量，Redis Stream 做异步任务，Redis 做缓存/限流，Apache Tika 做文档解析，对象存储保存上传文件。

### 2.5 核心链路：RAG 知识库

#### 2.5.1 上传与解析

链路：

```text
用户上传文档
  -> 文件校验和对象存储
  -> Apache Tika 提取文本
  -> 文本清洗
  -> 分块
  -> 向量化
  -> 写入 PostgreSQL + pgvector
```

要点：

- Tika 负责从 PDF、DOCX、Markdown、TXT 等文档中抽取文本。
- 文本清洗主要处理空行、异常字符、过长段落、格式噪音。
- 分块要避免太短没有语义、太长超过模型上下文或影响检索精度。
- 向量化后写入 pgvector，查询时做相似度检索。

#### 2.5.2 检索与问答

链路：

```text
用户问题
  -> 查询改写/补全
  -> 向量化问题
  -> pgvector TopK 相似度检索
  -> 过滤低相似度片段
  -> 组装 Prompt
  -> LLM 生成答案
  -> SSE 流式返回
```

答题重点：

- RAG 不是只把全文塞给模型，而是先检索相关片段。
- TopK 和相似度阈值是为了平衡召回和噪声。
- 查询改写可以让用户短问题更适合检索。
- SSE 流式输出改善等待体验。

#### 2.5.3 高频追问

问：为什么不用 Elasticsearch？

答：

> 这个项目主要是语义检索，核心是向量相似度查询。PostgreSQL + pgvector 可以同时承载业务数据和向量数据，架构更轻，适合个人项目和中小规模场景。如果后续需要更强的关键词检索、复杂过滤和大规模检索，可以引入 Elasticsearch 或专门的向量数据库。

问：RAG 如何减少幻觉？

答：

> 主要从三方面做：第一，检索阶段用相似度阈值过滤低相关内容；第二，Prompt 中明确要求基于知识库上下文回答，不确定就说明无法从材料判断；第三，答案生成时保留上下文片段，便于后续做引用或人工校验。

问：文档分块怎么设计？

答：

> 分块核心是保留语义完整性和控制长度。一般会按段落、标题或固定长度切分，同时保留一定 overlap，避免关键信息被切断。这个项目中我更关注工程链路，分块策略可以继续优化，比如按 Markdown 标题层级、PDF 段落结构或语义边界切分。

问：pgvector 怎么查？

答：

> 文档片段会存储对应 embedding 向量，查询时先把用户问题向量化，然后在 pgvector 中按向量距离做相似度排序，取 TopK 片段作为上下文。距离度量可以是 cosine、inner product 或 L2，具体取决于 embedding 模型和建表配置。

### 2.6 核心链路：Redis Stream 异步任务

#### 2.6.1 为什么用 Redis Stream

适合回答：

> 简历分析、知识库向量化和报告生成都属于耗时任务，如果同步处理，用户请求会一直阻塞，体验差，也容易超时。所以我用 Redis Stream 把任务生产和消费解耦，接口先创建任务并返回任务 ID，后台消费者异步处理，前端轮询或查询任务状态。

#### 2.6.2 状态流转

```text
PENDING
  -> PROCESSING
  -> COMPLETED / FAILED
```

可讲：

- PENDING：任务创建，等待处理。
- PROCESSING：消费者已领取任务。
- COMPLETED：成功写入分析结果或报告。
- FAILED：失败并记录错误原因。

#### 2.6.3 可靠性设计

可以讲：

- 消费者组：避免多个消费者重复处理同一消息。
- ACK：任务成功后确认消息。
- Pending 恢复：消费者异常退出时，未 ACK 消息可被重新领取。
- 失败重试：模型调用或解析失败时按策略重试。
- 内容哈希去重：相同文档避免重复分析或重复入库。

高频追问：

问：为什么不用 Kafka？

答：

> Kafka 更适合高吞吐、大规模日志和消息系统。这个项目的异步任务量不大，而且本身已经使用 Redis，Redis Stream 可以满足消费者组、ACK、Pending 恢复等需求，架构更轻量。生产级大规模场景下可以替换为 Kafka 或 RocketMQ。

问：怎么避免重复消费？

答：

> 第一是消费者组加 ACK，正常情况下每条消息只被一个消费者处理。第二是业务层要做幂等，比如任务状态已经 COMPLETED 就不重复执行，文档内容用哈希去重，报告生成也可以基于任务 ID 做唯一约束。

问：消费者挂了怎么办？

答：

> Redis Stream 有 Pending List，消费者读取但未 ACK 的消息会保留。后续可以通过 auto-claim 或类似机制把超时 Pending 消息转移给其他消费者继续处理。

### 2.7 核心链路：统一面试评估架构

#### 2.7.1 你要讲清楚的点

不是“让模型打个分”这么简单，而是：

```text
面试记录
  -> 按问题/回答整理
  -> 分批评估
  -> 结构化输出
  -> 多批结果二次汇总
  -> 失败降级兜底
  -> PDF 报告导出
```

#### 2.7.2 为什么要分批评估

答：

> 长面试记录一次性塞给模型，容易超过上下文窗口，也容易导致结构化输出失败。分批评估可以控制每次输入长度，先对局部回答进行评价，再对所有批次结果做二次汇总，稳定性更好。

#### 2.7.3 结构化输出

可讲：

- 模型输出不是自由文本，而是尽量要求 JSON/对象结构。
- 结构化输出便于后端解析、入库、前端展示和 PDF 导出。
- 失败时可以加修复型 Prompt 让模型按 schema 重新输出。

问：结构化输出失败怎么办？

答：

> 我会把结构化解析失败当作可恢复错误处理，比如限制输出格式、加入 JSON schema 或字段说明，并在失败时追加错误原因让模型修复输出。如果多次失败，就降级为保留原始文本或标记失败，避免整条链路阻塞。

### 2.8 核心链路：语音面试 WebSocket

#### 2.8.1 技术链路

```text
浏览器采集音频
  -> WebSocket 上传音频片段
  -> 服务端 ASR 转文字
  -> LLM 生成回复
  -> TTS 合成语音
  -> WebSocket/前端播放
  -> 保存对话记录
```

#### 2.8.2 可讲亮点

- WebSocket 适合实时双向通信。
- ASR 负责语音识别，TTS 负责语音合成。
- 服务端 VAD 用于判断用户说话结束。
- 流式字幕让用户看到识别过程。
- 手动提交用于避免自动断句不准。
- 暂停/恢复用于控制会话状态。

问：为什么不用 HTTP？

答：

> 普通 HTTP 更适合请求-响应模式，而语音面试需要持续上传音频、实时返回字幕和语音结果，是双向持续通信，WebSocket 更合适。

问：语音面试有什么难点？

答：

> 难点主要是延迟、断句、回声和状态管理。延迟来自音频上传、ASR、LLM 和 TTS 多个环节；断句不准会影响面试节奏；AI 语音可能被麦克风再次录入形成回声；另外还要维护当前问题、用户回答、暂停恢复和异常断开状态。

## 3. 项目二：MINICLAW 本地 AI Agent 平台

### 3.1 项目一句话

> MiniClaw 是我独立设计实现的本地 AI Agent 平台，核心是把 CLI、IM 入口和工具系统接入同一个 Agent 执行引擎，实现任务拆解、工具调用、MCP 扩展、上下文管理、权限审批和长任务恢复。

### 3.2 为什么这个项目有价值

不要说“我做了一个类似 Claude Code 的东西”，容易被追问过深。可以说：

> 我做 MiniClaw 主要是为了理解 Agent 工程化问题：模型如何规划任务，如何安全调用工具，如何管理上下文，如何处理失败重试，如何把长任务拆成可执行步骤。这些能力和企业内部智能助手、运维助手、知识库助手有相通性。

### 3.3 架构讲法

四层：

1. 交互入口层  
   CLI、飞书、微信等入口统一转成任务请求。

2. Agent 执行层  
   ReAct + Plan-and-Execute，负责任务理解、计划生成、工具选择、结果回填、步骤推进。

3. 上下文工程层  
   Prompt 分层、上下文压缩、会话摘要、长期记忆、BM25 历史检索、状态恢复。

4. 工具运行时层  
   Tool Runtime、MCP、文件读写、Shell、Web 抓取、Todo、代码搜索等基础工具。

### 3.4 ReAct 与 Plan-and-Execute

#### 3.4.1 ReAct

ReAct 的核心：

```text
Thought -> Action -> Observation -> Thought -> ...
```

适合：

- 需要边推理边调用工具。
- 信息不完整，需要搜索/读取文件/执行命令。
- 任务步骤不确定。

#### 3.4.2 Plan-and-Execute

核心：

```text
先生成计划 -> 按步骤执行 -> 根据结果调整计划
```

适合：

- 长任务。
- 多步骤开发/排查。
- 需要进度管理。

#### 3.4.3 你为什么混合使用

答：

> 纯 ReAct 灵活，但长任务容易漂移；纯 Plan-and-Execute 有结构，但计划一开始可能不准。所以我采用混合方式：先生成粗计划，再在每一步内部用 ReAct 调用工具和根据观察结果调整。

### 3.5 Tool Runtime 与 MCP

#### 3.5.1 Tool Runtime 要解决什么

- 工具注册：有哪些工具、工具名、参数 schema、权限等级。
- 工具调用：模型输出工具调用请求后，由运行时执行。
- 参数校验：避免模型传错参数。
- 权限控制：高风险工具需要审批。
- 结果回填：工具结果转成模型可理解的 Observation。
- 故障隔离：工具失败不导致整个 Agent 崩掉。

#### 3.5.2 MCP 是什么

可以这样说：

> MCP 可以理解成一种把外部工具和资源标准化接入大模型应用的协议。它让 Agent 不需要为每个工具写死接入逻辑，而是通过统一的工具描述、参数 schema 和传输方式动态发现和调用工具。

#### 3.5.3 高频追问

问：Tool Calling 和 MCP 有什么区别？

答：

> Tool Calling 更像模型侧的一种能力，模型决定调用哪个工具以及传什么参数；MCP 更偏工具接入协议，解决外部工具如何被发现、描述、调用和返回结果的问题。两者可以配合使用：模型通过 Tool Calling 选择工具，工具可以来自 MCP Server。

问：怎么避免模型乱调用危险工具？

答：

> 我会给工具做风险分级，比如只读文件是低风险，写文件、执行 Shell、删除文件是高风险。高风险工具需要 HITL 人工审批，参数也要做白名单/路径限制/命令限制，执行前展示给用户确认。

问：schema 清洗是什么意思？

答：

> 有些外部工具暴露的 schema 可能字段太复杂、描述太长或者包含模型不需要的信息。schema 清洗就是把工具参数描述压缩成模型更容易理解、上下文成本更低、风险更可控的形式。

### 3.6 上下文工程

#### 3.6.1 为什么需要上下文工程

Agent 做长任务时会遇到：

- 上下文窗口有限。
- 工具结果越来越多。
- 历史步骤会干扰当前判断。
- 模型容易忘记最初目标。
- 多个子任务之间信息混杂。

#### 3.6.2 你的机制

可以讲：

- Prompt 分层：系统规则、任务目标、当前计划、工具说明、历史摘要分层组织。
- 上下文掩码：不同子任务只看到必要信息。
- 阶梯压缩：历史消息从原文变成摘要，再变成关键状态。
- 会话摘要：保留目标、已完成步骤、关键结论、待办。
- BM25 历史检索：需要历史细节时再检索。
- 自动记忆提取：沉淀长期偏好或项目事实。

#### 3.6.3 高频追问

问：为什么不用直接把全部历史塞进去？

答：

> 第一是上下文窗口有限，第二是成本高，第三是过多无关历史会干扰模型判断。长任务更适合保留结构化状态和摘要，必要时再检索原始历史。

问：上下文压缩会丢信息怎么办？

答：

> 压缩确实可能丢信息，所以需要分层处理：关键目标、约束、决策和未完成事项必须保留；普通日志和重复内容可以压缩；涉及代码、命令、错误信息时尽量保留原文引用或可检索索引。

## 5. Java 后端高频技术题

### 5.1 Spring Boot 是什么

答：

> Spring Boot 是基于 Spring 生态的快速开发框架，核心是自动配置、起步依赖和约定优于配置。它让我们可以快速搭建 Web 服务、接入数据库、Redis、日志、监控等能力。

追问：你平时怎么分层？

答：

> 一般是 Controller 接收请求和参数校验，Service 处理业务逻辑，Repository/Mapper 负责数据库访问，DTO/VO 做请求和响应模型，Entity 对应持久化对象。复杂项目还会把基础设施能力单独拆出去，比如文件解析、Redis、AI 调用等。

### 5.2 MyBatis 和 JPA

你简历写 MyBatis，但当前项目用 JPA。答题要稳：

> MyBatis 更偏 SQL 显式控制，适合复杂查询和对 SQL 优化要求高的场景；JPA 更偏 ORM，简单 CRUD 开发效率高，但复杂查询和性能优化时要注意生成 SQL。我的项目里 JPA 用得多，但 MyBatis 的基本 XML/Mapper/动态 SQL 我也了解。

### 5.3 事务

问：事务的四大特性？

答：

- 原子性：要么都成功，要么都失败。
- 一致性：事务前后数据满足约束。
- 隔离性：并发事务之间互不干扰到一定程度。
- 持久性：提交后数据持久保存。

问：Spring 事务什么时候失效？

答：

- 同类内部方法自调用，没经过代理。
- 方法不是 public。
- 异常被 catch 掉没有抛出。
- 抛出的是受检异常但未配置 rollbackFor。
- 数据库引擎不支持事务。

### 5.4 索引

问：为什么索引能加速查询？

答：

> 索引本质是额外的数据结构，MySQL 常见是 B+ 树。它可以减少扫描数据量，把全表扫描变成树搜索。代价是占空间，并且插入、更新、删除时需要维护索引。

问：什么情况索引失效？

答：

- 对索引列使用函数或表达式。
- like 以 `%` 开头。
- 类型不匹配导致隐式转换。
- 联合索引不满足最左前缀。
- OR 条件部分字段无索引。
- 数据量太小或优化器判断全表扫描更快。

### 5.5 Redis

问：Redis 常用数据结构？

答：

- String：缓存、计数器、分布式锁值。
- Hash：对象字段。
- List：简单队列。
- Set：去重集合。
- ZSet：排行榜、延迟队列。
- Stream：消息队列、消费者组。

问：缓存穿透、击穿、雪崩？

答：

- 穿透：查询不存在的数据，绕过缓存打到 DB。解决：缓存空值、布隆过滤器。
- 击穿：热点 key 过期，大量请求同时打 DB。解决：互斥锁、逻辑过期。
- 雪崩：大量 key 同时过期或 Redis 故障。解决：随机过期时间、多级缓存、限流降级。

问：Redis Stream 和 List 区别？

答：

> List 可以做简单队列，但缺少消费者组、消息 ID、ACK、Pending 恢复等完整消息队列能力。Stream 更适合多消费者异步任务处理。

### 5.6 Java 并发

问：线程池参数？

答：

- corePoolSize：核心线程数。
- maximumPoolSize：最大线程数。
- keepAliveTime：非核心线程空闲存活时间。
- workQueue：任务队列。
- threadFactory：线程创建工厂。
- handler：拒绝策略。

问：为什么用线程池？

答：

> 复用线程，减少创建销毁开销；控制并发数量；统一管理任务队列和拒绝策略；避免无限创建线程导致系统资源耗尽。

问：synchronized 和 ReentrantLock 区别？

答：

> synchronized 是 JVM 关键字，使用简单，自动释放锁；ReentrantLock 是 JUC 显式锁，支持可中断、公平锁、尝试加锁和多个 Condition，但需要手动释放。

### 5.7 JVM

问：JVM 内存区域？

答：

- 堆：对象实例，GC 主要区域。
- 方法区/元空间：类元信息、常量等。
- 虚拟机栈：方法调用栈帧、局部变量。
- 本地方法栈：Native 方法。
- 程序计数器：当前线程执行位置。

问：GC Roots 有哪些？

答：

- 虚拟机栈中引用的对象。
- 方法区静态变量引用的对象。
- 常量引用的对象。
- Native 方法引用的对象。
- 活跃线程对象等。

问：如何排查内存问题？

答：

> 先看现象，比如 OOM、频繁 Full GC、响应变慢。然后通过日志、监控、堆 dump 分析对象占用，检查是否有集合未清理、缓存无限增长、线程泄漏或大对象频繁创建。

## 6. AI 应用高频技术题

### 6.1 Prompt Engineering

问：Prompt 怎么设计？

答：

> 我一般会把 Prompt 分成角色、任务目标、输入数据、输出格式、约束条件和示例几部分。对于结构化输出，会明确字段含义和 JSON 格式；对于 RAG，会把检索上下文和用户问题分开，并要求模型基于上下文回答。

### 6.2 RAG 和微调区别

答：

> RAG 是在推理时检索外部知识，把相关上下文提供给模型，适合知识频繁更新、需要引用企业文档的场景。微调是改变模型参数，更适合学习固定风格、领域任务或输出模式。企业知识库问答一般优先 RAG，因为更新成本低、可追溯性更好。

### 6.3 向量检索和关键词检索区别

答：

> 关键词检索依赖词面匹配，适合精确词、编号、名称；向量检索基于语义相似度，可以找到表达不同但含义相近的内容。实际系统里可以混合使用，关键词保证精确召回，向量检索提升语义召回。

### 6.4 流式响应

问：SSE 和 WebSocket 区别？

答：

> SSE 是服务端到客户端的单向流，适合大模型文本生成这种服务端持续推送场景；WebSocket 是双向通信，适合语音面试、实时协作等需要客户端和服务端持续互发消息的场景。

### 6.5 Agent 是否可靠

答：

> Agent 的问题是自主性强但不稳定，所以工程上要加约束：工具 schema、权限审批、任务计划、步骤检查、失败重试、上下文管理、日志记录和人工接管。不能完全相信模型自由执行。
